# 项目管理系统架构与工作流梳理

## 1. 当前系统想解决什么

这套系统的核心不是“聊天工具”，而是把实验室的协作过程沉淀成可追溯的项目资产。

当前的底层思路是：

- `Project` 负责承载业务对象
- `Task` 负责承载执行节点
- `ProjectLog / Timeline` 负责记录过程
- `Knowledge / Meeting / Chat` 负责补充上下文
- `AI` 负责把聊天、文档、群聊内容变成短日志，而不是单纯催办

一句话概括：

**项目是骨架，任务是节点，日志是时间线，AI 负责提炼和归档。**

## 2. 整体架构

## 2.1 前端层

主要页面：

- `ProjectListPage.tsx`
  - 项目列表
  - 项目详情
  - 项目日志/时间线
  - 群聊与话题
  - AI 助手配置
  - 群聊待归档工作台

主要职责：

- 展示项目、任务、日志、群聊、知识等信息
- 发起项目编辑、任务创建、日志沉淀、批注、删除等操作
- 管理员人工复核低置信度群聊归档

## 2.2 API 层

当前以 `backend/app/routers/projects.py` 为主入口，覆盖：

- 项目 CRUD
- 项目成员
- 项目日志
- 项目时间线
- 项目简报
- 项目群聊
- 飞书 Base 群聊数据源

建议后续按领域拆分为：

- `project_core`
- `project_logs`
- `project_briefing`
- `project_chats`
- `project_ingest`

## 2.3 数据层

核心表：

- `projects`
- `tasks`
- `project_logs`
- `project_log_comments`
- `project_relations`
- `project_chats`
- `project_chat_topics`
- `project_chat_messages`
- `ai_chat_submissions`
- `lark_doc_watches`
- `lark_base_chat_sources`
- `lark_base_chat_messages`

这些表的角色可以理解为：

- `projects / tasks`：业务主表
- `project_logs / comments`：项目过程记忆
- `project_chats / topics / messages`：群聊上下文
- `ai_chat_submissions / lark_doc_watches / lark_base_chat_messages`：AI 和飞书输入的原始材料层

## 2.4 AI 归档层

AI 归档入口目前有三类：

1. 飞书机器人文本消息
2. 上传的 `.txt / .md / .markdown`
3. 飞书云文档链接
4. 飞书 Base 群聊数据

处理逻辑：

1. 收原始文本
2. 规则初筛
3. 项目候选匹配
4. 大模型二次精炼
5. 生成短日志
6. 写入项目日志
7. 原始材料保留到底层表中，方便追溯

## 3. 关键模块说明

## 3.1 项目日志 / 时间线

项目日志是统一沉淀层。

它会把这些信息合并到一个时间序列里：

- 手工项目日记
- 自动项目日志
- 审计记录
- 任务更新
- 会议纪要
- 群聊话题

对应接口：

- `GET /api/projects/{project_id}/logs`
- `GET /api/projects/{project_id}/timeline`
- `GET /api/projects/{project_id}/briefing`
- `POST /api/projects/{project_id}/diary`
- `POST /api/projects/{project_id}/logs/{log_id}/comments`
- `DELETE /api/projects/{project_id}/logs/{log_id}`

当前策略：

- 原日志只读
- 允许批注和修正
- 不允许直接改原文
- 删除日志为单独动作

## 3.2 项目简报

项目简报来自时间线的近 24 小时窗口聚合。

输出内容：

- `headline`
- `summary_lines`
- `risks`
- `decisions`
- `action_items`
- `knowledge_seeds`

作用：

- 给项目负责人一个短时间窗口的压缩视图
- 避免从长日志里人工翻找

## 3.3 飞书云文档归档

工作流：

1. 用户把飞书云文档链接发给小卷
2. 系统读取正文
3. 大模型理解内容并匹配项目
4. 生成短日志写入项目
5. 自动建立 `watch`
6. 后续文档更新时做增量比对
7. 只归档新增内容，不重复写前文

关键点：

- 原文不整段搬到项目日志
- 项目日志只写短摘要和结构化要点
- 增量策略优先支持“持续往文档末尾追加”

## 3.4 飞书 Base 群聊数据归档

工作流：

1. 注册一个飞书 Base 群聊数据源
2. 系统拉取记录到本地消息池
3. 按 `群 + 人 + 日期` 聚合成分析批次
4. 先做规则匹配，再走大模型理解
5. 置信度 `>= 0.90` 自动写入项目日志
6. 置信度不足时进入“待归档工作台”
7. 管理员手动指定项目后归档或忽略

这样做的原因：

- 自动化能处理确定性高的部分
- 不确定内容不强行落库
- 人工复核承担最后一层质量控制

## 4. 当前主要工作流

## 4.1 项目创建与推进

1. 新建项目
2. 设置负责人、成员、标签、分类
3. 生成或编辑工作流节点
4. 在项目下快速创建任务
5. 成员推进任务
6. 关键过程写入项目日记
7. 项目页统一查看日志、简报、任务、群聊、知识

## 4.2 手工项目日记

1. 在项目详情页填写简短日记
2. 可选关联任务
3. 标记“重要”或“待确认”
4. 写入 `project_logs`
5. 自动进入时间线和项目简报

## 4.3 AI 对话归档

1. 把 AI 对话文本 / 文件 / 云文档发给小卷
2. 系统识别项目、阶段、日志类型
3. 大模型二次精炼
4. 生成短日志
5. 回消息告知“已录入项目日志”

输出目标不是复述，而是形成短日志：

- 有时间
- 有阶段
- 有摘要
- 有决策 / 风险 / 后续动作

## 4.4 群聊复核归档

1. Base 自动导入群聊数据
2. 高置信度自动写项目日志
3. 低置信度进入待归档工作台
4. 管理员查看群聊摘要
5. 选择项目后人工归档
6. 或直接忽略

---

## 5. 这套系统现在的边界

当前已经解决的：

- 项目、任务、日志、知识的统一承载
- AI 文本 / 文件 / 云文档归档
- 飞书群聊话题同步
- 飞书 Base 群聊离线归档
- 项目日志批注修正
- 项目日志删除

当前仍然要继续演进的：

1. 路由和页面文件还偏大
2. 项目阶段模型还不够强
3. 前端测试还缺
4. 群聊 / 文档 / AI 归档的置信度反馈还可以更细
5. 后续最好把运行期 schema 迁移进一步升级为正式 migration 体系

## 6. 推荐的下一阶段拆分

建议把后续开发按 4 条线推进：

## 6.1 项目过程线

- 项目日志
- 项目简报
- 阶段节点
- 风险与决策视图

## 6.2 协同输入线

- 手工日记
- AI 对话归档
- 云文档归档
- 群聊归档

## 6.3 审核治理线

- 待归档工作台
- 低置信度人工复核
- 忽略 / 归档审计
- 数据质量追踪

## 6.4 资产沉淀线

- 项目知识
- 会议纪要
- 项目关系
- 复盘与模板

---

## 7. 现在最重要的一句话

当前这套系统已经不是“任务板 + 聊天补充”。

它正在变成：

**以项目为核心，以日志为过程，以 AI 为归档助手的组织记忆系统。**
